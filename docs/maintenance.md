# 维护与接入

## 修改界面

颜色、间距与文字样式集中在 `app/ui/theme/CardDockTheme.kt`。`FunctionCard`、`SnapshotFields`、`StatusBadge` 等组件可在其他页面复用。页面只消费 `PrototypeState` 并调用 `PrototypeActions`。

不要在 Composable 的函数体、状态收集回调或页面切换中启动读取。通过明确按钮事件调用动作，避免重组造成重复执行。

## 修改演示内容

1. 在 `TemplateCatalog` 中调整规则和字段标签。
2. 在 `DemoDeviceGateway` 中调整对应固定对象的字段。
3. 在 `MockRuleCompiler` 中维护受支持的关键词。
4. 更新该类场景的测试，确认字段缺失、目标错配会失败。

模板中 `sourceId` 和 `targetKey` 必须对应实际模拟对象。设备响应返回自身观察到的目标，不能原样回显请求的目标来绕过核验。

## 接入真实需求编译器

在 `app/ai` 增加 `RuleCompiler` 实现，并在 `AppContainer` 替换 Mock。接口仍返回受约束的 `CompileResult`，不能把任意代码或脚本作为可执行结果。

如果模型输出不符合 schema 或缺少支持的目标，应返回明确失败，并让现有引擎继续验证。API 密钥不应放进 Android 源码或 APK；真实服务接入和凭据架构需要单独设计。

## 接入真实设备

通过 `DeviceGateway` 返回 `Ready`、`NeedsUser` 或 `Failed`。快照必须包含观察到的来源、目标标识和字段；无法可靠识别目标时不要返回成功。

平台相关实现放到 `app` 的实际功能包。真正涉及权限、无障碍服务和页面交互时才增加相应组件，并保留中断、取消、错误对象与失败不覆盖旧结果的测试。

当前协议只支持读取。如果需要点击或多阶段任务，应先设计动作的确认、取消点、幂等性与恢复规则，再扩展核心协议。

## 替换持久化

实现 `CardStore` 即可更换存储。保持三个约定：

- `load() == null` 只代表首次使用；空列表代表用户选择保留空空间。
- `save()` 完整替换集合；失败抛出异常，不能报告部分成功。
- 不会静默丢弃无法识别的 schema；升级时显式迁移。

原型用独立 `schemaVersion` 文件格式，不提供历史版本迁移。增加字段时同时考虑 `@Serializable` 默认值与旧文件兼容测试。

## 迁入现有 GitHub 仓库

当前工程不包含你的现有仓库历史。建议在骨架整改 PR 合并之后，从最新 `main` 建立 `feat/carddock-prototype`，按下面顺序迁入：

1. 对照现有配置合并 `core` 模块、依赖版本和 `src/main/kotlin` 路径；不要整包覆盖原有 Gradle 文件。
2. 迁入核心模型、端口、规则、会话与单元测试。
3. 迁入实际需要的 app 适配器、界面、资源与手写容器。
4. 合并 CI 与本 ADR，运行完整验证命令。
5. 审查 diff，确保没有构建缓存、本地 SDK 路径、签名材料或无用模板。

若当前整改 PR 尚未合并，原型可先独立运行。依赖基础骨架的功能修改不必混进同一个整改 PR。

## 代码约定

- 一个文件聚焦一种职责；不为单次调用增加空接口或继承层。
- 新能力先确定业务接口，再添加平台实现。
- 把时间、ID、设备和存储作为依赖注入，测试不依赖真实账号或当前时钟。
- 保留 `CancellationException`，不要用宽泛异常处理吞掉取消。
- 新增测试针对可观察行为，例如重复点击只执行一次、失败保留旧结果。
- 新增包只为实际代码创建，不使用空目录占位。
