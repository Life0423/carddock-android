# ADR 0001：原型的模块与执行边界

- 状态：本原型采用
- 日期：2026-11-09
- 范围：CardDock `0.1.0-prototype`

## 背景

首版需要验证“需求 → 规则 → 试运行 → 确认保存 → 重复执行”的体验。真实设备接入与模型能力尚未完成，因此必须让这些依赖可以替换，同时保持工程规模适合早期迭代。

## 决策

### 两个模块

`core` 使用纯 Kotlin/JVM，包含模型、规则、端口、执行引擎和原型业务状态。`app` 负责 Android 生命周期、Compose、模拟适配器、文件存储与依赖装配。

暂不把每一层或页面拆成独立 Gradle 模块。没有实际代码的目录不创建，也不引入 Hilt、导航框架、网络层或通用 Base 类。

### 编译与执行分开

`RuleCompiler` 只将需求编译为模板和规则。`RuleEngine` 执行已保存的 `RuleSpec`，每次刷新无需再次经过编译器。

当前规则是封闭的、版本化的数据结构：`assertTarget`、`readField`、`requireField`。未知版本和非法步骤在读取设备前失败。扩展规则需要同时增加语义验证、执行分支及相关测试。

### 一个观察快照

一次执行只向 `DeviceGateway` 读取一个快照。引擎核对来源和目标，然后从同一份字段集合提取结果，避免把不同时间、不同对象的字段拼成一个结果。

这只定义读取契约。未来涉及操作页面或多个交互阶段时，需要另外设计可恢复的执行协议，不能在现有 `inspect` 中悄悄塞入任意副作用。

### 状态与内容分开

卡片的 `snapshot` 保存最近一次有效内容；`run` 保存最近一次运行状态。失败、等待接管和取消不会抹去已核验内容，也不会伪造新的成功时间。

创建草稿不属于已保存卡片。修改需求会清除预览，试运行成功后仍需用户确认保存。草稿关闭后取消任务，并用编辑会话标识阻止迟到结果覆盖新草稿。

### 串行设备通道

所有卡片刷新与创建试运行共用一个 `Mutex`。同一张卡去重，不同请求排队。等待用户接管时释放通道；完成模拟接管后从头重新核验。

当前不实现跨进程任务恢复和后台运行。应用进程结束后，持久化的进行中状态在下次启动时标记为中断。

### 应用级生命周期

`AppContainer` 持有运行协调器与应用级 coroutine scope。Activity 重建只重新订阅状态，不重启执行。`ViewModel` 是薄绑定，Composable 不直接访问端口。

这不保证 Android 在后台保活。真正的长期任务需要后续独立决策。

### 原子文件持久化

使用 `CardStore` 接口隔离存储，Android 实现用 `AtomicFile` 保存版本 1 JSON。集合修改串行化，短暂磁盘提交与内存状态发布共同完成，取消不能把两者拆开。

不存在文件与空列表有不同语义：首次使用创建示例卡；用户删空后保持空列表。读取损坏数据时停止写入原文件，用户明确重置后才替换。

## 取舍

优势是核心可直接单测，界面能独立渲染，真实设备与模型接入可以从明确入口替换。

代价是 `core/session` 当前带有原型情景控制，文件存储每次保存完整集合，且只有一个空间和最近一次运行记录。实际需要多空间、查询历史或大量卡片时，再提取演示控制并替换持久化实现。

本决策不规定正式版的模型供应商、设备协议、数据库或后台执行机制。
